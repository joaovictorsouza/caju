# Brief e contrato U-1: UI integrada (`CajuUI`)

Formato da skill `caju-track-brief`. Base: [briefs/onda-1.md](onda-1.md) (§4, trilhas U-1a e U-1b), ADR 0002 (DSL e reatividade), ADR 0013 (layout por faixas), ADR 0012 (texto), ADR 0014 (lição dos *parameter packs*), ADR 0015 (RHI) e o rascunho [ADR 0026](../adr/0026-ui-display-list-e-dsl.md). Números marcados `(?)` não foram medidos.

**Este PR publica só o CONTRATO** (assinaturas, fronteiras e dependências), em rascunho. As assinaturas abaixo são **nível de contrato**: ainda não existem em código, não foram compiladas (Swift não existe no ambiente de nuvem; o CI valida quando a implementação chegar) e podem mudar em revisão. Nenhuma trilha consumidora começa antes do aceite deste PR (regra de contratos da Onda 1).

## 1. Trilha, diretórios, o que não toco
- **Dono:** `Sources/CajuUI` e seus testes. Subdiretórios propostos: `Core/` (U-1a, **sem `import CajuRHI`**) e `Render/` (U-1b). A fronteira é a *display list*. Como o `Package.swift` é um alvo só, a regra "`Core/` não importa `CajuRHI`" é verificada por `scripts/check-forbidden.sh` (extensão a combinar com o dono do script) e por revisão.
- **Não toco:** `Package.swift`, CI, `CajuUILayout` (P-4), `CajuText` (P-5), `CajuRHI`, `CajuInput`, `CajuRender`.
- **Faltam no `Package.swift` (pedido a S-0):** alvo de teste `CajuUITests` (hoje a UI só tem `CajuModulesTests`), entrada de benchmark da UI em `CajuBenchmarks` e, se o contrato de shaders do R-1a exigir, o alvo/etapa de shader. Nada disso é criado neste PR.

## 2. Camadas e fronteiras
```
 View (DSL)          ──►  Reconciliador / slot table  ──►  Núcleo retido (nós + CajuLayoutTree)
 @State / @Observable     (body em lote por View)              │  layout (ADR 0013) + medida de texto (CajuText)
                                                               ▼
                                              Construtor da display list     ◄── U-1a (puro, headless)
 ═══════════════════ CajuUIDisplayList (contrato, §4) ═══════════════════════════
                                                               ▼
                                   Batcher (instâncias SDF/MSDF)  ──►  RHI    ◄── U-1b
```
- **U-1a** (núcleo): DSL, `ViewBuilder`, `@State`, slot table, reconciliação, reatividade em lote, integração com `CajuUILayout`/`CajuText`, widgets básicos, **produção** da display list, eventos de ponteiro. Toda a lógica roda **headless** (Linux/CI), sem GPU.
- **U-1b** (render): consumo da display list, batcher, SDF (retângulos e sombras), MSDF (texto), envio do atlas, pipeline/PSO, goldens.

## 3. DSL (U-1a): assinaturas de contrato
**Nomes (a decidir, ver §8-1):** o rascunho usa o prefixo `Caju` em tipos (decisão do dono: prefixo `Caju*`), `CajuLabel` no lugar de `Text` (o módulo `CajuText` já existe) e modificadores sem prefixo.

### 3.1 `@State`, ambiente e observação
```swift
@propertyWrapper public struct CajuState<Value> {            // slot table: ver §3.2
    public init(wrappedValue: Value)                         // valor inicial: usado só no 1º mount
    public var wrappedValue: Value { get nonmutating set }   // set: grava no slot e marca a View suja
    public var projectedValue: CajuBinding<Value> { get }
}
@propertyWrapper public struct CajuBinding<Value> { get/set via ponteiros de slot, sem closures por quadro }
@propertyWrapper public struct CajuEnvironment<Value> { public init(_ key: CajuEnvironmentKey<Value>) }

// @Observable (Observation): 1 tracking por View; onChange só marca bit de suja (ADR 0002).
// Disponibilidade em Android real depende da medição de S-0 (ver §6).
```

### 3.2 Slot table e identidade
- **Identidade posicional** pela estrutura estática do `ViewBuilder` + `id(_:)` / `ForEach(id:)` explícitos (ADR 0002).
- `CajuStateTable`: armazenamento **contíguo** de slots, indexado por `(CajuUINodeID, slotIndex)`; `CajuUINodeID` = índice + geração (mesmo padrão de `CajuLayoutNodeID`). Alocação **só no mount** (caixa tipada do valor); nunca em quadro estável. O `Value` do slot é gravado por tipo concreto, sem existencial no caminho de leitura/escrita.
- **Tempo de vida:** slots de uma subárvore desmontada são liberados e a geração sobe; um `CajuBinding` antigo vira *no-op* seguro (nunca acessa slot de outra View).
- **Limite de profundidade 128**, igual ao layout (ADR 0013): a reconciliação é recursiva e limitada.

### 3.3 Reconciliador, quadro e erros
```swift
public struct CajuUIRuntime: ~Copyable {
    public init(configuration: CajuUIConfiguration) throws(CajuUIError)
    public mutating func setRoot<V: CajuView>(_ root: V) throws(CajuUIError)
    /// Um quadro: (1) drena a lista de Views sujas e reexecuta `body` em lote;
    /// (2) reconcilia e atualiza o `CajuLayoutTree`; (3) mede texto alterado;
    /// (4) `layout(in:)`; (5) reconstrói só os trechos da display list afetados.
    /// Sem nenhuma mudança e mesmo tamanho: só checa a sujeira e devolve `revision` igual.
    public mutating func update(availableSize: CajuVec2, time: Double) -> CajuUIUpdateResult
    public var displayList: CajuUIDisplayList { borrowing get }
    public mutating func handle(_ event: CajuUIPointerEvent) -> CajuUIEventResult
}
public struct CajuUIUpdateResult: Sendable { public var revision: UInt64; public var changed: Bool; public var layoutPasses: UInt8 }
public enum CajuUIError: Error, Sendable, Equatable { case depthLimitExceeded, nodeCapacityExceeded, duplicateID, invalidRoot, … }
```
Erros tipados (`throws(CajuUIError)`); dado externo (árvore vinda de "UI como dado", futuro) é hostil: sem `!`/`fatalError`/`precondition`.

### 3.4 Medida de texto e layout (decisão proposta, ver ADR 0026)
O ADR 0013 deixou aberto texto com quebra de linha. Proposta: o integrador mede o rótulo com `CajuTextLayout` e atualiza a folha (`CajuLayoutKind.leaf(.fixed(…))`); para rótulos com `maxWidth`, **no máximo 2 passadas por quadro**: layout → remedir só os rótulos cuja largura final mudou → layout. Sem callback de medida em `CajuUILayout` na v1 (evita PR de contrato em P-4 agora). Se a 2ª passada estourar o orçamento, abre-se PR de contrato em `CajuUILayout` (ver §8-2).

## 4. Contrato central: a display list (fronteira U-1a ↔ U-1b)
**Princípios:** dados planos e contíguos, só tipos `BitwiseCopyable`, **sem pack, sem existencial, sem closures, sem `String`** no caminho quente (lição do ADR 0014: *packs* custaram ~10× por *witness tables*). Ordem do array = **ordem de pintura** (de trás para a frente). A U-1a escreve; a U-1b só lê.

```swift
public enum CajuDrawKind: UInt8, Sendable { case rect, glyphRun, image, pushClip, popClip }

public struct CajuDrawCommand: Sendable, BitwiseCopyable {     // 48 bytes (?), alinhado; tamanho fixo
    public var kind: CajuDrawKind
    public var layer: CajuUILayerIndex       // UInt16: índice na tabela de propriedades de desenho (§4.2)
    public var frame: CajuUIRect             // moldura final em coordenadas de UI (após layout), px lógicos
    public var color: CajuColor              // preenchimento (rect), tinta (glyphRun) ou tint (image)
    public var shape: CajuUIShapeParams      // raio por canto, espessura/cor de borda, sombra (blur, offset, cor)
    public var range: CajuUIRange32          // glyphRun: faixa em `glyphs`; image: `textureSlot`; clip: índice
}

public struct CajuUIGlyphInstance: Sendable, BitwiseCopyable { // já posicionado; uv do atlas MSDF
    public var origin: CajuVec2              // canto do quad em coordenadas de UI
    public var size: CajuVec2
    public var uvMin: CajuVec2; public var uvMax: CajuVec2
    public var atlasPage: UInt16
}

public struct CajuUIDisplayList: Sendable {
    public private(set) var commands: ContiguousArray<CajuDrawCommand>
    public private(set) var glyphs: ContiguousArray<CajuUIGlyphInstance>
    public private(set) var layerProps: ContiguousArray<CajuUILayerProps>   // §4.2
    public private(set) var revision: UInt64          // sobe a cada mudança de comandos/glifos
    public private(set) var propsRevision: UInt64     // sobe quando só layerProps mudou
    public private(set) var dirtyCommands: Range<Int>?  // faixa alterada desde o último consumo
    public private(set) var atlasDirty: CajuUIAtlasDirty?  // espelha CajuGlyphAtlas.dirtyRect
    public let viewport: CajuUIRect; public let scale: Float   // px lógicos → px físicos
}
```
### 4.1 Regras do contrato
1. **Capacidade reservada** na criação (`CajuUIConfiguration.maxCommands`, `.maxGlyphs`, `.maxLayers`); em quadro estável, reconstruir **reaproveita** o armazenamento (`removeAll(keepingCapacity:)`), **0 alocação**. Estourar capacidade é erro tipado, não crescimento silencioso.
2. **Ordem e clip:** `pushClip`/`popClip` aninham (profundidade máx. 16 `(?)`). O batcher converte em *scissor* retangular; clip arredondado fica fora da v1.
3. **Imutável durante a leitura:** U-1b lê o quadro `N` enquanto a U-1a só escreve o quadro `N+1` depois (mesmo *thread* na v1; com Game Thread própria no Android, ADR 0008, a entrega é por troca de dois buffers, a decidir em V-1/R-1 `(?)`).
4. **Mudança só de desenho** (opacidade, deslocamento, escala, scroll) altera **apenas `layerProps`** (`propsRevision`), sem tocar `commands`: o batcher reaproveita as instâncias e só reenvia a tabela pequena (equivale a `graphicsLayer`, ADR 0002).
5. **Dedução barata de "nada mudou":** `revision` e `propsRevision` iguais ao quadro anterior ⇒ U-1b não faz trabalho de CPU nem reenvia buffers; só reemite os mesmos draw calls (ou reutiliza o *render bundle* quando existir, R-1).
6. **Coordenadas:** origem no canto superior esquerdo, y para baixo (igual a `CajuUILayout`); conversão para NDC fica no batcher.

### 4.2 Tabela de propriedades de desenho
```swift
public struct CajuUILayerProps: Sendable, BitwiseCopyable {
    public var opacity: Float; public var translate: CajuVec2; public var scale: Float
    public var clipRect: CajuUIRect?   // scroll/overflow; nil = sem recorte extra
}
```
Camadas são subárvores retidas escolhidas pela U-1a (raiz, `ScrollView`, nós com `opacity`/`offset`/`scaleEffect`). Opacidade de grupo composta por `layer` exige *offscreen* só se o grupo tiver sobreposição; v1 aplica opacidade por comando (multiplica o alfa) e documenta a limitação `(?)`.

### 4.3 O que o batcher (U-1b) produz a partir da lista
- Cada `rect` → **1 instância** de quad instanciado com SDF (raio, borda, sombra no mesmo shader); cada `glyphRun` → N instâncias MSDF (1 por glifo); `image` → quad texturizado.
- **Regra de mescla:** comandos consecutivos com mesmo `(pipeline, textura/atlas, scissor)` entram no mesmo draw call; a ordem de pintura nunca é alterada. Meta: **≤ 40 draw calls** na tela de loja `(?)` e **instâncias escritas direto no buffer do RHI** (anel de *upload* do quadro), sem arrays intermediários.
- Entrada do RHI: `CajuRenderDevice`/`CajuCommandBuffer` e `CajuUploadBudget` (ADR 0015); atlas MSDF via `CajuGlyphAtlas.pixels` + `dirtyRect` enviados como cópia parcial.

## 5. Divisão U-1a / U-1b e dependências
| | **U-1a (núcleo)** | **U-1b (render)** |
|---|---|---|
| Entrega | DSL, `ViewBuilder`, `@State`, slot table, reconciliador, reatividade em lote, widgets básicos, construtor da display list, ponteiro | Batcher CPU, SDF (rect/sombra), MSDF (texto), atlas, pipeline/PSO, goldens |
| Testa | 100 % headless, Linux/CI; *dump* textual da display list como golden | **U-1b-cpu:** batcher → buffers de instâncias com `CajuNullDevice` (headless). **U-1b-gpu:** goldens Metal/Vulkan |
| Depende de | `CajuUILayout` (pronto, P-4), `CajuText` (pronto, P-5), `CajuCore`; **S-0** (alvo `CajuUITests`, benchmark, `Observation` em Android); **I-1** só para tipos de ponteiro (a U-1a define `CajuUIPointerEvent` mínimo e adapta quando I-1 publicar) | Contrato de render da **R-1a** (§5.1); **V-1** para golden em Vulkan; U-1a (display list estável) |
| Não depende de | `CajuRHI`, GPU, R-1 | — |

### 5.1 O que depende de R-1a (explícito)
Só a **U-1b-gpu**. Pedidos concretos ao contrato de R-1a:
1. **Ponto de inserção do passe de UI** no *frame graph*: passe final, após o 3D, no alvo do *swapchain* (ou textura de composição), com *load/store* definido.
2. **Cache de PSO** e como registrar pipelines de UI (SDF e MSDF, mistura alfa pré-multiplicada).
3. **Anel de upload por quadro** (buffer dinâmico para instâncias) e política de `CajuUploadBudget`.
4. **Pipeline de shaders Slang offline** (quem compila, onde ficam os `.spv`/`.metallib`) e o contrato de recursos (UBO de quadro: viewport, escala).
5. **Harness de golden** de GPU compartilhado (comparação por tolerância), para não duplicar.
6. **`WorldAnchor`** (ancorar UI a ponto do mundo 3D) precisa da extração de câmera da R-1a; fica **fora** da U-1a e entra depois do contrato de extração.
Enquanto R-1a não publica contrato, a U-1b entrega só a parte **cpu** (batcher sobre `CajuNullDevice`) e nada de shader.

## 6. Dependências abertas e riscos
- **S-0:** alvo `CajuUITests`, benchmark da UI, e o resultado de `Observation` no S22+. Se `@Observable` falhar em Android, a U-1a segue só com `@State`/`CajuBinding` e `CajuObservableBox` próprio (decisão em ADR novo, não neste).
- **HarfBuzz/FreeType:** aprovados em princípio (onda-1 §9-3). A U-1a usa o shaper puro (ADR 0012) para latino; se um *script* exigir, PR dedicado de `Package.swift` e atualização do ADR 0012. Nada disso bloqueia o contrato.
- **Custo de `body`:** meta < 100 ns `(?)` (ADR 0002) ainda sem medida; benchmark entra com a primeira implementação.
- **Compilação:** sobrecargas fixas de `ViewBuilder` crescem o tempo de checagem de tipos; medir no CI (plano §risco de compilação).
